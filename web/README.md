# WinScore Web

Browser shell of the SCORE editor. The Rust crate `rust/crates/score-web` (WebAssembly, via wasm-bindgen) opens, renders, hit-tests, edits and saves `.mus` files. This TypeScript/Vite app paints its display lists on a canvas and handles input.

## Requirements

- Rust with the `wasm32-unknown-unknown` target (`rustup target add wasm32-unknown-unknown`)
- `wasm-bindgen` CLI of the same version as the crate: `cargo install wasm-bindgen-cli --version 0.2.129 --locked`
- Node 24 (`nvm use 24`)

## Run

```sh
cd web
npm install
npm run dev        # builds the wasm, copies the samples, serves http://localhost:5173
```

**Published** at https://pfefferniels.github.io/winscore/: `.github/workflows/web.yml` runs the Rust tests, the build and the smoke test on every push and deploys `dist/` from `main` to GitHub Pages.

`npm run build` writes a self-contained static site to `web/dist/` (relative paths; wasm, fonts and samples included). `npm run preview` serves it at http://localhost:4173.

Environment variables: `CARGO_TARGET_DIR` (default `rust/target`), `WASM_PROFILE` (default `release`). For commands in words, `TYPESAFE_API_KEY` (Jev) and `ANTHROPIC_API_KEY` or `CLAUDE_API_KEY` (Claude), from the environment or a Git-ignored `web/.env.local`: `npm run dev` and `npm run preview` pass the page's requests on under `/ai/…` with these keys (`ai-proxy.ts`), so they never reach the browser. Behind an HTTP proxy, Node needs `NODE_USE_ENV_PROXY=1` for that.

Frame times while dragging: `npm run build && npm run perf [FILE.mus …]` (default the largest sample); it fails if a frame during the drag takes more than 50 ms. Drags re-render only the moved items (`rust/crates/score-web/src/live.rs`); the full render follows on drop.

Screenshots of the built app: `npm run build && node scripts/screenshots.mjs OUT_DIR [name='sample=mozart.mus&zoom=200' …]` (needs `npx playwright install chromium` once).

The command field: `npm run check:ai` (no browser: expressions, values lifted from commands, scripts run through score-web) and, after a build, `npm run smoke:ai` (the field by the selection and at a click on the paper, typing read at every keystroke and tried on the score, Escape taking it back, sliders and undo in the built app, a new staff and a menu command by words, a note repeated with its slider, a command written while another runs on other items, and cancelling one, with Jev and Claude answered by canned replies). `npm run eval:jev` sends 137 commands to the real Jev (`TYPESAFE_API_KEY`), on eight notes, on a mixed selection and at a place on the paper (which, as in the app, is about a whole score), and compares the intents with the expected ones, and for those it leaves to Claude whether they are complex (`scripts/jev-eval.ts`; `JEV_CASES=beam,and` runs some; Jev's answers are shown for those it misreads, and for all with `JEV_ANSWERS=1`): in October 2026, in four runs of the first 131, all of them three times and 129 once with jev-1.13, and all 137 with the repeats (a few are read at about the 50 % they need: *staccato and stems up*, *accent them and move up a step*), a median of about 150 ms per reading. The questions for picks, new items and the editor's commands cost about 8 ms of it (143 against 135 ms for the questions without them, the same commands asked in turn). `npm run eval:claude` gives Claude (`CLAUDE_API_KEY` or `ANTHROPIC_API_KEY`, `CLAUDE_MODEL` and `CLAUDE_EFFORT` to pick one) the commands Jev leaves to it, on items of `mozart.mus`, runs each script on the score and checks what it did (`scripts/claude-eval.ts`; `CLAUDE_LIMIT=1` asks one at a time, as the app does, with the system prompt cached). In October 2026, one at a time, Opus 5.5 at low effort, Sonnet 5.5 and Haiku 5.5 each wrote the first 7 correctly: Sonnet in about 2 s (1.6–6), Haiku in about 2.8 s (1.5–5), Opus in about 3.7 s (2.3–5.5); Sonnet then did all 14 (chords, bars, selecting, beaming, a refusal, lines between notes, a new staff), in about 2–3 s each. With three complex commands added (*double the melody a third below*, *retrograde the melody*, *invert the melody around its first note*), four at a time, Sonnet at low effort, Opus at low and Opus at medium each did all 17: Sonnet in about 2 s (1.5–10), Opus at low in about 3 s (1.9–21), Opus at medium in about 4.5 s (2–21), its scripts the most thorough (an inversion refits stems, beam and slur; deleting the eighths takes their beams). With lyrics added (*add missing "-" for lyrics*, the syllables of one word left without their hyphens), Sonnet at low effort and Opus at medium each did all 18. `CLAUDE_CASES=beam,bar` runs the cases whose command has one of these words. `CHROMIUM=/path/to/chrome` runs the browser scripts with another Chromium than Playwright's.

Crops of the painted page for judging the painter by eye: `node scripts/zoom-shots.mjs OUT_DIR [sample=mozart.mus] [at=X,Y] [size=W,H] [zooms=50,100,400] [dprs=1,2] [dist=DIR]` writes one crop per zoom and pixel ratio, its top-left corner at page point `at` (engine units); `dist` takes another build, for comparing before and after.

## Using it

The page is drawn by the Rust renderer alone. The app bar holds Undo and Redo, the score's name (with "Unsaved changes" after an edit), zoom, the side panel switch and `?` (or F1). There is no menu bar: `?` lists every command, grouped as WinScore's menus group them (File, Edit, Insert, Layout, View: "Edit ▸ Copy" below is Copy under Edit there), each a button with its shortcut or the SCORE command it sends, so it can be typed in the command field next time; then the keys and gestures. Its name typed in the command field runs a command too (*save*, *zoom in*, *export svg*), with no model.

- **Start**: without a score the page shows a start screen: **New score** (an empty page, `MusFile::empty`), **Open…**, and the bundled samples (`assets/samples/`), which are also under File in the `?` list. Music typed in the command field on an empty score (*add c e g 4 8 8* at a click on its paper) makes its first staff, as SCORE's `IN 1` does. New and Open ask before unsaved changes are discarded.
- **Open** a `.mus` file from File ▸ Open (⌘O / Ctrl+O) or by dropping it on the window. **Save** (⌘S / Ctrl+S) downloads it.
- **Export SVG** and **Print** (⌘P / Ctrl+P) render the page for print (no staff numbers or other screen aids) as a paper-sized SVG from `score_render::svg`, drawn as SCORE's PostScript output draws it: lines and the outlines of filled shapes with a 1/150 inch pen and round joins, text in the bundled faces (`fonts/README.md`) with installed equivalents behind them in each font stack. The exported file embeds the faces its text uses, only those styles, as WOFF2 data (`src/svg-fonts.ts`), so it looks the same in any viewer. Print puts the same SVG into the page, where a print stylesheet shows it alone on paper of the score's size: the printer gets vectors, and a PDF saved from the print dialog has real paths and text.
- **Zoom**: −/+ buttons or the `+` and `_` keys, the percent list, Fit width (↔), View ▸ Actual size, or ctrl/⌘ + wheel (pinch) around the pointer.
- **Selection**: click an element; Shift-click adds or removes; Escape clears. A click selects the item whose drawn outline is under the pointer; where there is none, WinScore's own rule picks the item with the nearest reference point within 12 px. The side panel shows the last selected item: buttons for WinScore's edit-mode commands (← → ↑ ↓ for L1 R1 U1 D1, Flip, Center, Delete, previous and next item), then its settings in groups (`src/item-fields.ts`), each with a control that fits what it holds, read from and written into SCORE's packed parameters: for a note its pitch in the clef in force (type `F#4`, `Bb3`, or a letter for the nearest one; ↑/↓ step it), accidental, stem up or down, value, dots and tuplet, mark, offset; for a rest its symbol and value; clef types, key signatures by key, meters, barline types, hairpins and line types, slur, bracket and ending types, beams, staves, symbols (Choose… opens the symbol grid), numbers, boxes, text sizes. A list's choice, a button or a box applies at once; a typed value on Enter or when the field is left, ↑/↓ step it (Shift: by ten); every setting is one undo step. Below them **All parameters** (closed by default, remembered in the browser) lists P1…Pn with the help's label for each, including those the help describes but the item does not store, and sets any other parameter by number. The panel can be hidden (View ▸ Side panel); the choice is remembered in the browser.
- **Editing**: drag selected items (Shift locks to one axis by WinScore's rule, Escape cancels), arrows move by one P3 space or scale step, Page Up/Down by 4 steps, Home/End by 10 spaces (WinScore's edit-mode keys), `[`/`]` one staff up/down, Enter / Shift+Enter to the next / previous item, Delete, ⌘Z/Ctrl+Z undo, ⇧⌘Z/Ctrl+Y redo. Ctrl/⌘-drag or the middle button pans. **Save** downloads the edited `.mus`. All editing runs in `score-edit`: moves, deletes, commands, drags and the undo history. Drags send the cursor position and keep the grab offset; score-edit computes P3/P4 as the engine does, with P4 in whole steps for notes, rests, clefs, keys and meters.
- **Several items** are edited together: the panel shows the settings they share (all of them for items of one kind; Staff and Position across kinds), each with their value where they agree and *Mixed* where they differ (a checkbox half set). A value typed or picked goes to every item, ↑/↓ step each from its own value, and the change is one undo step (`Editor::set_params_of`, "Set P7, P9 of 12 items"). A setting that fits only some of them (dots, not on grace notes) says "9 of 12" and changes those. A selection of several kinds has a button per kind that narrows it to that kind; a selection of text items has the font menu.
- **Copy and paste**: ⌘C / Ctrl+C copies the selected items, ⌘X cuts them (one undo step), ⌘V pastes copies as one undo step, selected so they can be dragged or nudged at once; on a touch screen Edit ▸ Cut, Copy and Paste do the same. The copies keep their arrangement and their pitches (P4). After a click or tap on the page since the copy, their lowest staff goes to the clicked staff and their left edge to the click; otherwise they go where they were copied from. Where they would lie exactly on the same items (the originals, or an earlier paste), they move 10 spaces to the right, WinScore's End step, as often as needed, so Home puts one back over its original. ⌘D (Edit ▸ Duplicate) makes such copies of the selection beside it without touching the clipboard. Copied items travel as a `.mus` file of their own (`Score.copySelection`): on the system clipboard as base64 text, so ⌘V in another tab pastes them into that score, and kept in the page for Edit ▸ Paste, which pastes what was copied in this tab and outlasts opening another score. A copy is also what `PST` pastes from the command field. Fields, dialogs and selected text keep the browser's own copy and paste (`src/clipboard.ts`, `score_edit::clipboard`).
- **Handles**: a single selected item shows handles for what its parameters shape besides P3 and P4, worked out by `rust/crates/score-web/src/handles.rs` from where the renderer draws each part (`score-render`'s `line::shape`, `slur::shape`, `note::stem_end`, `beam::ends`, `barline::reach`). Round handles are ends: of lines and hairpins (P3/P4, P6/P5; a hairpin's end only sideways), slurs, ties, brackets and endings, beams (P4, P5, up and down only), the line after a trill or ottava sign (P6), a staff (P3, P6), and the top of a barline, which reaches the staff nearest the pointer (P4). Squares on the item's frame scale it about its reference point: clefs (P6, P7), symbols (P6, P7, keeping the part-extraction hundreds and the mirroring sign), numbers (P6), meters (P7), text (P6 at the corner, P7 at the top) and boxes and circles (P6, P7; the side opposite the handle stays, Shift keeps the proportions); a staff's top right corner sets its size (P5, or P14) about its bottom line. The round handle on a stalk turns symbols, boxes and text (P9) and numbers (P19), resting on right angles, with Shift in 15° steps. Amber diamonds shape the item: a slur's curvature (P7) and where it peaks (P10, resting at the middle), a bracket's or ending's height (P7), a hairpin's opening (P7, resting at the default), the bracket hooks at a line's ends (P11, P12), a note's stem length (P8, in half steps, keeping a grace slash), a staff's place (P4) and a text's spacing (P5). A drag sets the values live (score-edit's `Editor::adjust_begin` … `adjust_end`), shows them by the pointer and is one undo step named after the handle; Escape cancels. Side handles of a frame too small to hold them are left out; hovering a handle names it and shows a cursor for its direction.
- **Guides**: while items move or a handle is dragged, lines appear to what it lines up with, and it snaps onto them within 6 px (10 on a touch screen); ⌘/Ctrl held while dragging turns them off (`src/guides.ts`). They read the music: the staff's lines and spaces (named, e.g. "middle line", "1 ledger line above"), like items at the same level on the same staff (a row of dynamics), the same level as like items on other staves (labelled "level -5, as on staff 4", the item outlined), notes, rests and barlines on nearby staves (note heads by their middle), the middle of a bar, a line's or slur's other end ("level with the other end"), and for a staff's place the gaps between the page's other staves ("as between staves 8 and 7", "halfway between staves 5 and 3"); besides those, the edges and middles of like items, as in a drawing program. Edges meet edges, middles middles, reference points (where SCORE places an item) reference points, staff lines and levels; a handle meets all of them. Musical guides are dashed and labelled. score-web gives the shell every item's reference point and level (`Score.guideAnchors`) and the staves' lines (`Score.staffGeometry`).
- **Command field**: while something is selected (by any of the usual ways: a click, ⇧-click, a box), a field stands by it; a click or tap on empty paper opens it there, with nothing selected. What is typed on the page outside a form field goes into it, opening it where it is not (at the last click on the paper while that is in view, else at the top left of the view). There is no command bar: the field takes everything WinScore's command bar takes. A SCORE command line runs as on WinScore's command bar, on the selection if there is one (`FLI`, `R 5`, `U 2`, `I 5` to select item 5, `LJ 1 2`, `NOTE`, `IF … THEN …`, `"Allegro" 1 50`), and the engine's objection, if it has one, shows under the field with the line kept to be corrected. A command in words (*remove the stems*, *beam in pairs*, *make the notes gradually bigger*, *slur these notes*, *add staff*, *zoom in*) is read by a model at every keystroke, and under the field it says what it read and what that reaches (`→ Remove stems · 12 items`): the reading of the words typed so far shows at once, with a spinner while the newest words are read, so how the command is understood can be watched as it is written; with nothing selected it is about the whole score, and music it adds goes on the staff nearest the click, from the click to the staff's end (*add c e g* above a staff). **What Jev reads is tried on the real score at once, as the command is typed**: the newest reading's edit shows on the page, with what it changes selected, and gives way to the next one as the words change (or to why it cannot be done: *only notes shorter than a quarter take beams*). **Enter keeps it**, as one undo step named after the command; what it changed stays selected, and the field with it for the next command. Escape, an empty field, a SCORE line or other items selected take it back, and a score only tried on is not marked as changed. Commands Claude writes and the editor's own commands (*save*, *zoom in*) wait for Enter. A command Claude writes is **sent off**: the field is free at once for the next command, on these items or on others selected meanwhile, and a badge above the command's items shows it under way (its words, which Claude; × cancels it). Its edit lands on its own items when it is written, as its own undo step: if the field still stands by them it says what it did there, as for a command run at once; otherwise the selection stays where it is and the badge says what it did for a few seconds (clicked, it selects what the command changed, with its sliders if nothing came after). A command that cannot be done keeps its badge, saying why, until it is clicked (which puts it back in the field) or dismissed. An edit waits while something is dragged, a group command waits for its area or a slider is held; a command landing after another's takes that one's sliders away, as any later edit does. Numbers the command leaves open become sliders under the field (*make the notes gradually bigger*: from, to, curve; *beam in pairs*: notes per beam; *move up*: steps): dragging one takes the step back and does it again with the new value, live, still one undo step; another selection drops them. With a staff selected, *add notes c g d/f/a* writes the notes after the music on it through SCORE's input language (`score-input`): the values typed after them all (*add c e g 4 8 8*, *as 4 8. 16*), after each (*add c 4 d 8 e 8*) or one for all (*add c e g 8*), else the value Jev reads (*as eighths*), else quarters; the first note nearest the staff's middle line, each next one nearest the one before, unless octaves are typed (*c4*); chords as *c/e/g*, *r* a rest, *|* a barline. With other items selected, over their stretch; on an empty score, at a click on its paper, the notes make staff 1. Up and Down recall earlier lines. ⌘Z in the empty field undoes the last command; Escape empties it and gives the keyboard back to the page, where Escape deselects and the field goes (with nothing selected, Escape takes the field away).
  - **Reading a command.** *Jev* (TypeSafe's System One model, `ai-models.ts`) reads it while it is typed: one request of typed questions — which action, which items or which part of them, which property (every option of the side panel's settings of the kinds selected, as "Mark: Staccato"), which measure, direction, interval, notes per beam, which of the command's numbers is the amount, which of the items by their place, which new item, which of the editor's commands — answered with probabilities in about a seventh of a second (the field, when it appears, opens the connection with a one-question request, so the first command is read as fast). Every keystroke asks at once; the newest answer shows, and the requests asked before it go. A request Jev takes more than 3 s for counts as unread. Items picked out by place become a selection the edit then acts on (`ai-intent.ts`'s picks: the first, the last, every other one, every second one, the top or bottom notes of the chords, the highest or lowest note, the first or last of each bar, the first or last few with a slider for how many): *accent every other note*, *stems down on the bottom notes of the chords*, *staccato on the first three notes*, *add a slur over the first three notes*; picked out some other way (*the notes on the beat*), Claude writes it. *Select …* makes the items it names the selection (*select the top notes*, *select only the staccato notes*). *Repeat* pastes copies of the selection after it, as often as the command says (*repeat 3 times*, *repeat this bar twice*, a slider for how many): each a period on from the one before, the selection's stretch and the mean gap between its columns, so the music goes on as it went; where the copies would run past the staff's end, the selection and its copies are drawn closer, alike. **New items** go by the selection, on each of its staves (`create` steps): a barline, double, final or repeat barline after it (halfway to the next item), a clef, key signature, meter or start repeat before it (halfway from the item before), a dynamic, fermata, word (*cresc.*, *a tempo*, *pizz.* …), box, number or text at its first item, a slur, tie, hairpin, line, trill, 8va, 8vb, 15ma, pedal mark or ending over it from the first item to the last (over one item: up to the next), a slur's or tie's ends at its notes as SCORE's slur pass places them (opposite the stems, clear of the heads, off the lines); with nothing selected, at the place clicked; *add staff* makes one above the highest, as Insert ▸ Staff does. Code lifts a meter (*3/4*), a number and a quoted text (*add "dolce"*); Jev picks the key (*three flats*, *D major*), for the clef in force. At a place on the paper, a new item Jev is quite sure of wins over a property for the whole score (*add a fermata* there is one fermata, not one on every note), unless the command names the items it changes (*make all the clefs bass clefs*); a property with nothing to give (*add mf* to notes) is the new item too. **The editor's own commands** are commands in words as well: every command of the `?` list that can run now but the items under Insert (`menus.ts`'s `wordCommands`), as "Edit ▸ Copy": *save*, *undo*, *copy these*, *zoom in*, *hide the side panel*, *line up and justify*, *show the keyboard shortcuts*; Enter runs it as its button does. Two actions at once are read as two (*staccato and stems up*, *make them eighths, then beam in pairs*: values first, then beams, sizes, stems, places), when they can safely run together (no deleting, adding or SCORE lines, not the same answers twice; else Claude writes it), and a note value given alongside a beam (*8th beam*, *sixteenths beamed in fours*) when the command names it, not when it only names which notes (*beam the eighths*). Notes per beam count only when the command names a number (*pairs*, *4*, *fours*); else each run up to the barline is beamed, whatever the size of the selection. Code only lifts what a decision model cannot write: the numbers (spelt ones too, *two* to *twelve*, *twice*, *thrice*; not *one*, as likely a pronoun), the note names, a meter and a quoted text in the command (`ai-values.ts`), which Jev then chooses between. The answers make an intent (`ai-intent.ts`) and that an edit script. When Jev is not sure (below 50 %) or reads *something else*, Enter has *Claude* write the edit script itself: Sonnet 5.5 at low effort by default, the fastest of the three in the evaluation below, and for a command Jev finds **complex** (one more question of the same request, at 50 % or more, even when Jev hears an action in it: *add a c major arpeggio* is not *add c*: new music worked out from a description or from the music there, such as *double the melody a third below* or *retrograde the melody*, several edits that depend on one another, items and values worked out from others) Opus 5.5 at medium effort, as it is written while other commands go on; ⚙ picks either model (Sonnet, Haiku or Opus). Under the field the reading says which writes it (`↵ has Claude Opus write it`). Claude writes the script (structured output against the script's JSON schema), told the settings of every kind of item and WinScore's 383 edit words (`Score.editWords`). Readings are remembered for the session by their words and the kinds of items.
  - **Edit scripts** (`ai-script.ts`): steps on the command's items, narrowed by code, by a setting's value (*Mark is Staccato*) and by an expression: `setting` (a side-panel setting by name, so packed parameters are written as the panel writes them), `set` (a parameter), `move` (as the arrow keys), `delete`, `command` (an edit word on the items; a group command such as FLN runs with nothing selected and is given their area, `Score`'s `groupCommand` telling them apart; `STAFF` makes a staff above the highest, as Insert ▸ Staff does), `insert` (a line of music input in the region), `beam` (beams over runs of notes shorter than a quarter, then the engine's refit, FLN, fits stems, flags and beams) `select` (the items picked become the selection and what the later steps act on; nothing is edited), `create` (Jev's new items: an item of a SCORE creation word on each staff of the items, before, at, after or over them, else at the region), `repeat` (Jev's: copies of the items after them) and `add` (for each item picked, a new item whose parameters are values over it: *lines from note head to note head* is a line from each note's `x`, `level` to `next_x`, `next_level`, the next note on its staff; a text gets the step's characters, made as quick entry makes it: *add the missing hyphens* is a `-` centred between each syllable Claude picks by its `id` and the next text on its line). Claude is shown the items with their identities and every text's characters. Values may be expressions (`ai-expr.ts`) over the item's parameters, its identity (`id`), its place left to right (`t` from 0 to 1, chords counting once, systems top to bottom), its place in its bar (`bi == 0` the first of each bar; barlines count on every staff they cross), its chord (`level == chord_low` each chord's bottom note), the smallest, largest and mean value of each parameter over the items, the setting's current value and the knobs. A script of Claude's that fails to run goes back to it once with the error: it writes it again, or answers that the command cannot be done here and why (*only notes shorter than a quarter take beams*). score-edit makes the steps one undo step (`Editor::mark`, `combine`, `rollback`) and items keep their identity through sorting and undo (`Score.keys`).
  - **Keys.** Through `npm run dev` or `npm run preview` the server's keys are used (see above). Otherwise ⚙ takes a TypeSafe or Vercel AI Gateway key for Jev and an Anthropic key for Claude, kept in this browser. TypeSafe's API does not answer pages of other sites (CORS), so on a static site such as GitHub Pages Jev goes through Vercel's AI Gateway (`typesafe-ai/jev`); Claude's API answers pages directly.
- **Status line** (bottom): what the last action did and the selected item's P1…Pn, as WinScore lists the item in edit mode, or the engine's message; on the right the pointer's place on the paper.
- **Text**: Insert ▸ Text opens a dialog (text, font from WinScore's font menu as its `_NN` code, staff, P3, P4) and creates the items as SCORE's quick entry `"text" staff P3 P4` does. Double-click a text item to edit its characters where they stand, or edit them and pick a font in the panel.
- **Symbols**: Insert ▸ Symbol opens a searchable grid of every symbol in WinScore's bundled libraries, each drawn by the Rust renderer, with WinScore's names (`symblist.txt`).
- New items (text, symbols) go to the selected item's place, else to the last click on empty paper, else to the top staff at P3 100.
- **Group edit**: drag a box over empty paper to select the items inside. score-edit reads the box as WinScore reads a mouse-drawn area (`Editor::draw_box`): staves by their middle lines, P3 from x, a narrow box meaning the whole width. The Area commands under Edit (Move, Copy, Delete, Alter, Copy to staves) start WinScore's line-by-line dialogue: its question appears at the head of the command field (which opens for it where the paper was last clicked, and goes once it is answered), and the answer is typed there or given with the mouse (a box for the area; for the destination a click keeps the area's position on that staff, a thin line moves its left edge, a box rescales it); Cancel ends it without a change. `IF … THEN …` conditional edits go through the command field.
- The **Layout** commands send WinScore's LI (line up), J (justify), LJ, LJA (all systems) and TR (transpose); they are typeable in the command field too (`LJ 1 2` answers at once). LI, J and LJ ask for the lowest staff and the number of staves of the system, typed or given by drawing a box. When the engine would give up (unequal beats, no notes), its message appears in the status line.
- **Commands** of the `?` list: Insert holds WinScore's Items menu (codes 1–18), note and rest values and clefs; Edit its edit-mode and group-edit commands. Each sends the SCORE command from WinScore's command table (`src/commands.json`) with its tooltip; commands `score-edit` does not handle are left out. New items go to the selected item's staff and position.
- **Phones and tablets**: below 640 px wide the app bar keeps Undo, Redo, the score's name, the side panel switch and `?`, whose list fills the screen; zoom is by pinching or under View there; the side panel lies under the page, starts hidden, and its grip sets its height. On a touch screen (`pointer: coarse`) targets are larger and text fields are 16 px, which iOS does not zoom into. The page takes its own gestures (`touch-action: none`, `src/interaction.ts`): a tap selects (a finger picks within 24 px rather than 12) and on empty paper opens the command field there, a drag pans and glides on, a drag from a selected item moves it, two fingers pinch the zoom around the point between them, a long press adds or removes an item and a long press with a drag draws a box, a double tap edits a text where it stands; while a group command waits for its area, one finger draws the box and a tap answers it. A group command's question does not focus the command field there, so no keyboard covers the page. Where an on-screen keyboard covers the page without resizing it (iOS), the app follows the visual viewport. `?` lists the gestures.
- URL parameters for direct links: `?sample=mozart.mus&zoom=200&select=12`, or `?new` for an empty score.

## Conventions

- Page coordinates are engine units of 1/4000 inch, origin at the paper's bottom-left corner, y up.
- **Zoom**: 100 % shows the page at physical size on a 96-dpi screen (one CSS pixel = 1/96 in ≈ 41.7 engine units). This matches WinScore's own 100 % (zoom 64 of 256 in an `MM_HIENGLISH` view) on a 96-dpi display. The preset list is WinScore's zoom bar (10 … 500 %) plus larger steps; − and + change the zoom by a quarter, as WinScore's Reduce and Zoom do.
- **Painting** (`src/paint.ts`) no longer imitates WinScore's screen, whose GDI pen is one device pixel at every zoom. It draws the page as SCORE puts it on paper, after the prologue WinScore writes at the head of its PostScript output: lines have a physical pen, the shape's own width (score-render sets SCORE's print widths) or 1/150 in (`wdl lw`, `score_render::PEN`), so they thicken with the zoom; joins are round (`1 setlinejoin`) and caps butt; filled objects use the even-odd rule and are then outlined with the same pen (`gsave eofill grestore stroke`), so noteheads, beams and slurs gain half a pen on every side, as printed. Lines are at least a device pixel wide, so the thinnest pens (score-render's one-unit hairline, a print pen narrowed to almost nothing) draw one pixel; a polyline that ends where it starts (boxes, frames) is closed, so its first corner is joined like the others. Fill outlines with the default pen are at least half a pixel, since a whole one closes the gaps between beams at 75 % and less on a 1× screen while much thinner slurs fade to grey; thinner pens lower that floor in proportion, so a fill outlined with a hairline does not visibly grow. Pens under 1.5 px are drawn as hairlines of at most a pixel, which canvases draw several times faster. Horizontal and vertical shapes are snapped as the prologue's stroke adjustment (`setstrokeadjust`) snaps them: the pen rounded to whole pixels, odd pens on pixel centres and even ones on pixel edges, every point a whole number of pixels from the shape's first, so staff lines, stems, barlines and flat beams have crisp edges and equal widths at any zoom and pixel ratio. Curved and slanted outlines keep their exact positions and are antialiased. A filled shape of one outline (nearly all of them) is filled once, grown by half the pen, outward corners rounded and inward ones mitred: that covers what fill and outline cover and is several times faster in a canvas than a stroke wider than a pixel, which keeps painting as fast as the one-pixel pen was. Shapes off the canvas are skipped. Text sits on its baseline at the engine's y + 96 (folded into the display list's coordinates). The paper is white with a hairline edge and a soft shadow on a grey desk; WinScore's green page frame is gone.
- **Fonts**: see `fonts/README.md`. The engine positions every character itself, so the substitute faces only change glyph shapes, not positions. Each glyph stays at its fractional x (rounding it to a whole pixel made the letter spacing wobble by up to a pixel); a level baseline sits on a whole pixel. Glyphs keep their face's proportions, scaled horizontally only where the text sets its width apart from its height: the run's width over 0.4125 × its height, the ratio of the record header's fields for ordinary text (P6 = P7), so 1 for almost all text. The painter used to stretch them as GDI does, until the average character width of the Windows face GDI substitutes (Times New Roman, Arial, Courier New) matched the run's, a property of that face which SCORE's spacing ignores (Courier came out at 69 %). Outlined letters (`run.outline`) are stroked with the default pen, as the prologue's `false charpath lw stroke`. Rotated text turns about the cell's top-left corner (baseline plus the Windows face's ascent), for which the engine's positions of rotated characters allow (P9), and turns clockwise, following the line on which the engine places the characters (inferred, not observed on Windows).
